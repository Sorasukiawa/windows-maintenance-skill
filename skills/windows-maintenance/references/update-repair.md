# 更新、修复与固件

## Windows 完整性

顺序由前置状态决定，不把所有命令每轮重跑：

- 仅检查：DISM `/ScanHealth /English` 与 SFC `/verifyonly`，先保存输出和退出码。
- 已确认损坏且维修在授权内：保存日志、确认恢复资料，先 DISM `/RestoreHealth /English`，成功后 SFC `/scannow`。
- 修复完成：读修复结论，再用必要的 ScanHealth/verifyonly 证明当前健康；要求重启的状态单列。
- 失败：记录错误及日志，停止依赖步骤。修复源需匹配系统构建、版本、架构、语言和映像索引；不从第三方下载单独 DLL 覆盖。

RestoreHealth 返回 0 或 SFC 显示无冲突，都不能覆盖随后 ScanHealth 的 repairable 结论。
若复查仍有损坏，验收状态仍为未通过，组件库清理继续暂停；按新的 CBS 文件/错误证据决定下一次修复，不无依据重跑。

还原点或恢复环境不等于完整备份。还原点创建失败时明确缺失的恢复能力，评估本轮操作是否仍可继续。
一次源缺失不能通过循环修复或无依据重置更新组件解决。
修复会恢复受保护系统文件，可能还原此前精简；在报告里说明这一影响。
参考：[微软映像修复](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/repair-a-windows-image?view=windows-11)。

## 软件与 Windows Update

WinGet 先只查询候选，再按 `--id`、`--exact` 及已核对来源逐项升级；不要直接用 upgrade --all 代替筛选。
Unknown 是已装版本不可比较。先读客户端活动文件/关于页或自更新器，比较一致的版本口径。
启动器安装器版本和客户端版本可能是不同序列；不要仅为 Unknown 用 include-unknown 强装。
无适用更新返回码在核对官方定义和当前版本后可记“无需更新”，不是“本轮已升级”。
安装前记录精确包、官方来源、签名和必要配置；安装后重读版本，不能仅看退出码或下载成功。
浏览器后台旧进程仍运行时，记录磁盘新版与活动旧版；保存用户工作后再安排应用重启。
远程工具承载当前连接时，先确认备用连接/本地操作条件，避免更新切断唯一控制路径。
参考：[WinGet upgrade 参数](https://learn.microsoft.com/en-us/windows/package-manager/winget/upgrade)。

WUA 搜索范围、每项更新 ID、类型、ResultCode、HResult、RebootRequired 都应保存。
搜到驱动更新不能说 Windows 系统补丁已安装；无普通补丁只适用于当前更新源和扫描窗口。
Store “未匹配可升级包”不等于商店所有应用都最新；不覆盖自更新软件、便携版和测试渠道。
检查日志中的历史失败是否后来成功，避免重复修复已经恢复的服务。

### 配置迁移与启动定制

升级前保存关键配置的厂商导出或文件备份与哈希，并记录相关任务/服务/启动项的程序路径、参数和启用状态。
升级后对照关键设置与迁移记录：文件消失或哈希变化可能是路径/格式迁移，先区分正常迁移、重置默认与实际丢失，不立即覆盖新版配置。
确认设置丢失时优先使用厂商支持的导入；恢复旧文件前核对新旧格式、版本与设备适用性，确认可回退，并先备份新版生成的配置和启动状态。
兼容性检查包括设备绑定数据及新版所需权限/所有者；哈希不能证明这些条件满足，不把旧目录权限整套覆盖给新版。
确需文件恢复时，确认散热等关键控制仍可用，只短暂停止会写入这些文件的精确 UI/服务，按经核对的原路径恢复匹配文件并复查清单/哈希。
若任务或看门狗会重新拉起写入者，仅在恢复窗口内有界抑制对应项，并在结束时还原原状态。
把必要服务及原运行状态的恢复放入 finally 并验证；中途失败记录部分结果，利用所留新版状态回退，不继续覆盖不兼容配置。
比对并恢复仍受新版支持的定制启动参数；不能仅因任务仍存在就认定后台启动等行为保留。
版本、文件存在、哈希一致和服务 Running 分别只证明各自状态；通过应用设置/导出及实际运行行为核验关键配置已被采用。
无法读取应用设置或验证设备行为时，分开报告“文件已恢复/服务已恢复”和“设置采用尚未验证”，不宣称配置保留通过。

## 驱动与稳定性

精确硬件/子系统 ID、系统架构及 OEM 适用性优先于包名称或日期。
核对当前实际绑定 INF、组件类别、版本；音频支持组件版本不能和主音频驱动版本直接比较。
使用官方 OEM/厂商包或 Windows Update 精确适用项，核验签名与来源。
变更前导出当前对应驱动包并保存回退说明；导出目录只是文件备份，不保证一键恢复所有设置。
安装后核验绑定、问题码、服务及涉及的声音/网络/显示功能；不能只确认 DriverStore 里多了新包。
Code 22 表示禁用，Code 28 才是未安装驱动类线索，不自动批量启用原有禁用设备。
参考：[PnPUtil 支持的导出与驱动管理命令](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/pnputil-command-syntax)。

存在黑屏、0x116、频繁 nvlddmkm 或相关错误时，先保留转储、旧驱动与调校配置。
“最新”与“这台机器稳定”是两个判断；有证据时选择一个可比较的驱动版本做单变量验证。
不把驱动、CPU/RAM/GPU 调校和固件同时改变后宣称确定根因，也不通过加大 TDR 超时掩盖故障。
传感器/风扇工具停止或更新前，确认水泵与风扇还有可用控制方式并保存转速、灯效、LCD 配置。
运行轻负载时的温度正常、短暂零事件，都不足以验收游戏稳定性。

## 固件

主板 BIOS/UEFI/AGESA 不设固定排除；检查与更新范围遵循用户本次要求及本任务已有授权。
广义“更新电脑”不自动涵盖全部外设刷写。对需要刷写的具体设备，检查现有授权是否明确覆盖。
先准备可审阅条目：设备与硬件修订、当前内部版本、目标版本、官方链接/发布说明、适用性、供电/连接要求、失败恢复办法。
OSD/厂商工具读不到当前版本时标为未确认；USB 名称中的数字、应用版本不替代真实固件版本。
使用匹配设备的官方更新器；不要跨型号、跨厂商刷 VBIOS 或推断论坛包适用。
授权和条件都满足才执行；之后从设备重新读版本，安装器结束不等于设备已采用新固件。
关机断电、拔插、重启等步骤按厂商流程及现有授权安排，不能静默触发。
